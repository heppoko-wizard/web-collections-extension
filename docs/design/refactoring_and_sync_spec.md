# パネルのリファクタリングおよび同期ロジック刷新仕様書

## 1. 目的
`panel.js` の肥大化（1200行超）を解消し、保守性と信頼性の高い同期システムを再構築する。
「表示（UI）」と「ロジック（Sync）」を物理的に分離し、同期処理をバックグラウンドで安全に実行可能にすることを最終目標とする。

## 2. 現状の課題と解決策

### 2.1 UIモジュールの肥大化
*   **現状**: `panel.js` がUI描画、イベント、同期計算のすべてを担っている。
*   **策**: 役割ごとにファイルを分割し、各ファイルを200行程度に収める。

### 2.2 脆弱な同期アルゴリズム
*   **現状**: 更新時刻（`updatedAt`）のみを基準とした単純上書き。競合時にデータが消失する。
*   **策**: フィールド単位でのマージ、または論理削除を含む履歴ベースのマージへの移行。

### 2.3 ID衝突のリスク
*   **現状**: `Math.random()` ベースの短いID。
*   **策**: `crypto.randomUUID()` 等を用いた UUID v4 への移行（既存IDのマイグレーションを含む）。

### 2.4 モジュールシステムの古さ
*   **現状**: `importScripts` やグローバル変数に依存した古いスクリプト読み込み。
*   **策**: `manifest.json` に `"type": "module"` を追加し、ES Modules 形式へ全面移行する。

## 3. 新アーキテクチャ案（モジュール構成）

分割後の各モジュールは以下の責務のみを持つ。

### 3.1 UI・レンダリング層
1.  **`js/panel-ui.js`**: DOM要素の参照管理、ビューの切り替え、モーダル制御。
2.  **`js/panel-render.js`**: HTMLテンプレート生成。IndexedDBのデータをHTML文字列に変換する責務。
3.  **`js/panel-state.js`**: アプリケーションのグローバル状態管理。状態変更の通知（オブザーバー・パターン）。

### 3.2 コントローラー・イベント層
4.  **`js/panel-events.js`**: ボタンクリック等のイベントリスナー設定。ユーザー操作を各マネージャーへディスパッチする。
5.  **`js/panel-dragdrop.js`**: ドラッグ＆ドロップによる並べ替えロジックに特化。

### 3.3 同期・コアロジック層（最重要）
6.  **`js/sync-manager.js`**: 同期のオーケストレーター。`FolderSync` や `CollectionStorage` を組み合わせて同期フローを制御する。
7.  **`js/sync-strategy.js`**: データマージの具体的なアルゴリズム定義。時刻比較、競合検知、削除の伝搬を計算する。

### 3.4 バックグラウンド層
8.  **`js/background-handlers.js`**: `chrome.runtime.onMessage` のハンドリングを機能ごとに分散。`background.js` を軽量化する。

## 4. 同期プロトコルの刷新

### 4.1 IDの刷新
*   新規データ作成時は UUID を使用する。
*   既存の `xxxx-xxxx-xxxx` 形式のIDは、初回同期時またはマイグレーション時に UUID へ変換することを検討する。

### 4.2 マージアルゴリズム
*   **Last Write Wins (Field level)**: 全体の上書きではなく、プロパティ単位で新しい方を採用する。
*   **削除の同期**: `isDeleted` フラグと `updatedAt` を組み合わせ、クラウド側で削除されたデータをローカルにも波及させる。

## 5. 実装への指示事項

1.  **UIとSyncの完全分離**: `SyncManager` は `document` や `window` に依存してはならない。Service Worker 内でも動作可能にすること。
2.  **アトミックな更新**: `manifest.json` と各 `collection_*.json` の不整合を防ぐため、書き込み順序とエラーハンドリングを厳密に行うこと。
3.  **メッセージングの利用**: `panel.js` 内で直接同期関数を呼ぶのではなく、`background.js` を介して非同期に要求を出す構造に移行すること。
